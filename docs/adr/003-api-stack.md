# ADR-003: API: NestJS, Drizzle ORM, PostgreSQL

- **Status:** Accepted (approved by Ayush, 2026-10-05)
- **Date:** 2026-10-05

## Context

The API has many bounded areas (auth, problems, submissions, contests, rooms, AI, admin) with shared cross-cutting concerns (auth, validation, rate limits, tracing). The structure should be explainable in a design interview.

## Decision

NestJS with the Express adapter. One module per area; modules talk through services, never another module's repository (SD-§4). Drizzle ORM over PostgreSQL 16 with SQL migrations generated by drizzle-kit. Zod validates every boundary and errors leave as RFC 7807. The decorator runtime used by tsx/vitest emits no type metadata, so providers are always injected with explicit `@Inject(token)`.

## Alternatives considered

- **Express/Fastify without a framework:** less ceremony, but we would rebuild DI, guards and filters by hand.
- **Prisma:** good DX, but heavier runtime, and SQL-first migrations suit the schema constraints we rely on (unique `(submission_id, run_version)`, enums, citext).
- **TypeORM:** decorators fit Nest, but weaker typing for queries.

## Consequences

Clear module boundaries and a familiar DI model. Cost: Nest adds boilerplate, and the explicit `@Inject` rule must be followed or DI fails at runtime rather than at compile time.
